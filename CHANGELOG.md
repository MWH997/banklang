# Changelog

## Unreleased

### Added

- **Added IBM MQ.** `queue paymentOut manager "CSQ1" name "PAYMENT.OUT" output record Payment status outReason;` declares a queue, and `connectQueue` / `putMessage` / `getMessage` / `disconnectQueue` drive it. A queue is not a file and nothing about it goes through file control: the program connects to a queue manager, opens the queue as an _object_ described by an MQOD, and every operation is a `CALL` with a completion code and a reason code coming back. The call signatures, the structures, and the constants are IBM's, read out of the Application Programming Reference rather than remembered — `MQCONN(QMgrName, Hconn, CompCode, Reason)`, `MQOPEN(Hconn, ObjDesc, Options, Hobj, CompCode, Reason)`, `MQPUT(..., BufferLength, Buffer, CompCode, Reason)`, `MQGET(..., BufferLength, Buffer, DataLength, CompCode, Reason)` — as are the 48-character name limits (`MQ_Q_MGR_NAME_LENGTH`, `MQ_Q_NAME_LENGTH`) and every constant the emitted code names. `connectQueue` is `MQCONN` then `MQOPEN` and `disconnectQueue` is `MQCLOSE` then `MQDISC`, as single statements, because neither half is useful alone and splitting them would only create the two orderings that are wrong. Each control block is copied into a group of its own and every reference qualified: `CMQODV` declares `10 MQOD.` with fixed names beneath it, so a program with an input queue and an output queue has two of each and IBM's own samples — which copy each structure once — never meet the ambiguity. **A get has three outcomes, not two**: a message, an empty queue, and a failure. An empty queue is reason 2033 and the ordinary end of a drain, so folding it in with the failures would stop a batch every time it finished its work, and folding it in with success would process the message area again still holding the last message read; both branches are therefore required. Puts and gets run under syncpoint, so a payment is not visible to a consumer before the ledger posting that goes with it commits, and a get asks `MQGMO-NO-WAIT` because a batch that blocks on an empty queue never ends. The direction on the declaration decides which calls are allowed, since it is what the `MQOPEN` asked for, and reading an output queue is refused at compile time rather than at run time with reason 2037 (`BANK-MQ-002`). The status field is a reason code rather than a two-character status, so it is typed as a number. The job asks for the three things MQ needs and would not otherwise have: `MQM.SCSQCOBC` on `SYSLIB` so the copybooks resolve, `MQM.SCSQLOAD` at link time so the MQI calls resolve to the stub, and `MQM.SCSQANLE` with `MQM.SCSQLOAD` on `STEPLIB` at run time. Nothing outside z/OS supplies the MQI, so `runtime/BANKMQ.cbl` stands in and the precompiler replaces the copybooks with a local declaration of the fields the compiler sets — the executed test puts a message, overwrites the record, gets the message back, and drains the queue, so the record is proved to be filled from the message rather than left holding what the program already had, and the empty queue is proved to arrive as 2033. It is not IBM MQ: no queue manager, no persistence, no syncpoint, no channel.
- **`JSON PARSE` and `XML PARSE` are now executed locally rather than carried as a caveat.** Enterprise COBOL implements both; GnuCOBOL 3.2.0 compiles either, warns it has not implemented it, and then does nothing at run time — the record is left untouched, no exception is raised, and a program reading a payload runs clean and processes an empty record. That is the worst shape a divergence can take, because every local signal says the program worked. Both are now routed the way `EXEC SQL` and `EXEC CICS` already were: the precompiler rewrites `JSON PARSE` into one call on `BANKJSON` per item of the receiving record — the record is the schema, so asking for each item by name is the question the statement asks — and rewrites `XML PARSE` into the loop it is, with `BANKXML` returning one event per call and the generated handler performed for each. **What ships to z/OS is untouched** and keeps the statement it was written with. The registers could not come along: GnuCOBOL reserves `XML-TEXT` but only a real `XML PARSE` sets it, and a `MOVE` to it ends the run with a segmentation fault, so the handler is pointed at fields of the translator's own, reference-modified by the length of the event. `JSON-STATUS` and `JSON-CODE` are set with the values IBM documents — reason code 1 for "one or more data items had no matching JSON name/value pair", code 101 for text that "was zero-length, or consisted only of whitespace" — so the test the compiler emits after a parse is reached with a value it did not invent. `tests/parse-shims.test.ts` runs both and asserts the record was filled. The divergence list in `tests/gnucobol-coverage.test.ts` is down to one entry, `national`, which no shim can reach: it is an allocator difference, not a missing statement. `BANK-TYPE-025` still warns on every parse, because the stubs are scans and IBM's parsers are not — `runtime/README.md` lists what neither attempts.
- Added `restart <file> into <record> { ... } else { ... }`, the half of checkpoint/restart the compiler had never emitted. See **Fixed** below for why its absence was a defect rather than a missing feature.
- Corrected the IMS DL/I support to what IMS actually requires, after checking the conventions rather than assuming them. Four things were wrong in the first version and none of them failed to compile. **The I/O PCB was missing**: it comes first for every IMS program, `CMPAT=YES` being what IBM says to specify for a batch program, so omitting it shifted every database PCB by one and the program would have read the I/O PCB as its first database. **`ISRT` carried no search argument**, though the segment being inserted must always be identified by an unqualified one. **`GN` carried none either**, which makes it return the next segment of any type in hierarchical order rather than the one the database declares. And **`REPL` and `DLET` were reachable after a plain read**, where DL/I answers `DJ` and silently does not perform the update. `getHoldUnique` and `getHoldNext` were added for the last of these, and `BANK-DLI-002` now requires one before any update — a hold in an enclosing block covers a branch inside it, but a hold inside a branch does not travel back out, because the path that skipped it reaches the update unheld.
- Added IMS DL/I. `database accountDb pcb segment "ACCTSEG" key "ACCTID" record Seg status dbStatus;` declares a database, and `getUnique` / `getNext` / `insertSegment` / `replaceSegment` / `deleteSegment` each become one `CALL "CBLTDLI"` with the matching function code. An IMS program does not open a database or read it with file control: the region hands it a PCB, which is why the generated program takes one on the `PROCEDURE DIVISION` and never allocates it. The segment and key names sit on the declaration because the search argument is built from them once, and each is eight bytes — what DL/I carries, so a longer one is truncated into a name matching nothing in the DBD (`BANK-DLI-001`). `getNext` deliberately passes no search argument: it walks from wherever the last call left the position. The status field is required rather than optional, because the two characters DL/I leaves in the PCB are the entire error model — without somewhere to read them a `getUnique` that found nothing is indistinguishable from one that worked, and the program goes on to use whatever the segment area held last.
- Added `runtime/CBLTDLI.cbl`, a reference DL/I language interface in the same shape as `DSNHLI` and `DFHEI1`, so a generated IMS program can be executed rather than only compiled. It is not IMS: it evaluates no database, holds no segments, honours no hierarchy, and maintains no position. It reads a status per call from `dli-outcomes.txt` and puts it in the PCB, which is enough to reach the branches a program guards with its status test and nothing more. The test supplies a driver that allocates a PCB and calls the program, because that is how a region enters one.
- Assigning an enum field one of its members now emits `SET <condition> TO TRUE` rather than `MOVE "<member>"`, which is what the level-88 names generated beside the field have always been for — they were declared and never used. The `MOVE` repeated the spelling of the member in the procedure division, where it can drift from the 88 that defines it: rename the member and the `MOVE` still compiles, still runs, and writes a value no condition matches. The condition is qualified by its group for the same reason the `MOVE` was, since the record is emitted in working storage and again inside every `FD` that holds it. A local of enum type keeps its `MOVE` — a local is an `01` item the emitter only qualifies on collision, so a condition on one has no group to qualify it — and so does a field assigned from another field, which moves a value rather than choosing a member.
- Added `varying <min> to <max> length <field>` on a file declaration, which becomes COBOL `RECORD IS VARYING IN SIZE ... DEPENDING ON`. A fixed-length file pads every record to the longest one it might hold, and for a feed whose records differ by hundreds of bytes that is most of the dataset. The length field says how much of the record is in use — set before a write, filled by a read — and `textLength` pairs with it, being what the field holds rather than how wide it was declared. The bounds have to be a range and the file has to be sequential, since an indexed or relative dataset addresses a record by key or by position and a varying length would move it (`BANK-FILE-009`). The executed test writes an eleven-character record and a twenty-seven-character one and checks the file is under sixty bytes: padded to the declared eighty it would be a hundred and sixty.
- Added `call <name> using <record> on error { ... };` and `cancel <name>;` — a dynamic COBOL `CALL` and `CANCEL`, where the module is named by a value rather than written into the source. That is how a bank dispatches: a product code selects the module that prices it, and a new product ships as a new load module without relinking anything that calls it. The name has to be text and eight characters, because that is what a load module name is and a longer field is truncated to one that does not exist (`BANK-TYPE-029`). `on error` is the point of the feature: a static call that cannot be resolved fails at link time where somebody sees it, while a dynamic one fails in the middle of a batch — so a `call` without a handler is warned about, and the executed test calls one module that exists and one that does not and checks the program survives. `cancel` drops the loaded module so the next call gets its working storage as the compiler left it, and takes no handler because nothing is being entered.
- Added `search sorted`, which becomes COBOL `SEARCH ALL` — a binary search — together with the `ascending <field>` clause that declares a table's order as `ASCENDING KEY IS`. A linear scan of four hundred rate bands reads two hundred rows to find one; bisecting reads nine. COBOL will do it only on a table that says it is ordered and only on equality against that key, because anything else has no ordering to cut in half, and both are checked (`BANK-TYPE-028`). That check earns its place: `SEARCH ALL` on a table that is not actually sorted does not fall back to scanning it — it returns the wrong row, or reports no match on a row that is sitting there. `SEARCH ALL` sets the index itself, so unlike a plain `search` no `SET ... TO 1` is emitted before it. `ascending` and `sorted` are contextual, so both stay usable as field names.
- Added a second wave of intrinsics: `integerPart`, `fractionPart`, `sign`, `reverse`, and `textLength`. The first two split an amount into whole units and what is left of them, which is what a cash-handling or a settlement program does; `sign` says which way an amount moves without comparing it twice. `textLength` is `STORED-CHAR-LENGTH` rather than `LENGTH`, because a COBOL field's declared width is something the compiler already knows — what a variable-length record needs is what the field actually holds, trailing spaces excluded. `reverse` pairs with it for the check-digit algorithms that read a number backwards. Each takes its precision from whatever it is assigned to, the way `round` does, since none has a natural width of its own.
- Added tables of tables: `rates: decimal<9, 4>[3][4]` becomes nested `OCCURS`, three rows of four — a rate matrix by term and band, which is how a bank holds one. The bounds read outermost-first, so the first becomes the outer table; wrapping as each bracket was consumed would have nested them the other way round and silently transposed the matrix. COBOL subscripts the innermost data name with every dimension at once, so `book.rates[1][1]` becomes `RATES-ITEM OF BOOK (1, 1)` rather than `RATES (1) (1)`, and the inner dimension is named for you because nothing in the source names it and COBOL needs something to subscript. Each dimension gets its own `INDEXED BY`.
- Added initial values on record fields — `processed: binary<9> = 0;` — which become COBOL `VALUE` clauses. Working storage starts as whatever the region left there unless a field says otherwise, so a counter without one starts at an unpredictable number; saying it in the record rather than in an opening paragraph keeps the fact next to the field, where it cannot drift out of step when the record gains one. COBOL evaluates a `VALUE` when it compiles, so it has to be a written number, string, boolean, or enum member of the field's own type and short enough to fit (`BANK-COPY-006`) — text longer than its field would be truncated silently, so it is refused instead. A `redefines` field cannot carry one, having no storage of its own. The clause is dropped when the same record is written into an `FD`, where COBOL forbids it, and a `bool`'s existing `VALUE 'N'` is replaced rather than written beside it, which COBOL would reject as two clauses on one field.
- Added the arithmetic COBOL already knows how to do: `abs`, `min`, `max`, `mod`, `rem`, `annuity`, `presentValue`, `isNumeric`, and `toNumber`, each lowering to the intrinsic function that does it. The compiler was using seven of GnuCOBOL's hundred-odd intrinsics, and two of the ones it was not using are in the language because COBOL was written for this industry. `annuity` is the repayment factor of a loan, so `round(principal * annuity(monthlyRate, termMonths), "HALF_UP")` is a mortgage quote — £100,000 at 0.5% a month over 240 months gives £716.43, computed by COBOL rather than by this compiler. That is the point of routing to the intrinsic: a repayment factor worked out in a loop rounds differently, and the difference lands in a customer's final instalment. `mod` is what a check digit is. `isNumeric` asks whether a field from a flat file will convert before `toNumber` tries, which is the difference between rejecting a record and abending on it at three in the morning; both read grouping and a currency symbol, because `NUMVAL-C` does. `annuity`, `presentValue`, and `toNumber` take the scale of whatever they are assigned to, the way `round` does. The names are contextual, so `min`, `max`, and `abs` stay usable as fields, and the tests run a loan quote and check the payment against the number a mortgage calculator gives.
- Added `nested function`, a COBOL contained program. An ordinary function is a paragraph the program `PERFORM`s, sharing all its storage; a nested one is `PROGRAM-ID ... COMMON.` written inside the container before its `END PROGRAM`, with its own working storage and a real `CALL` boundary. What it buys is what the sibling programs a recursive function already becomes cannot do: it reads the module's records directly, because the container declares them `GLOBAL`. So a record parameter is not passed at all — the callee can already see it, and handing it over would be a second name for the same storage — while scalars still travel through `LINKAGE`. It cannot recurse (`BANK-TYPE-027`): COBOL forbids `LOCAL-STORAGE` in a contained program, so its locals are one copy shared by every invocation, and a recursive call would overwrite them on the way down and read the innermost call's values on the way back out — compiling, running, and returning the wrong number. `nested` is contextual and only in front of `function`, so it stays usable as a field name. The tests run one and check the arithmetic came back through the container's record.
- Added `json <text> into <record>`, which becomes `JSON PARSE` — the generate statement with the direction reversed. There is no `count`, because the document says where it ends, and a record carrying a `sensitive` field is fine here rather than reported: restricted data arriving from outside and landing in a field marked for it is the marking working, not an escape.
- Every `json ... into ...` carries a warning (`BANK-TYPE-025`). Enterprise COBOL implements `JSON PARSE`; GnuCOBOL 3.2.0 compiles it, warns that it is not implemented, and then does nothing at run time — the record is left untouched and no exception is raised, so a program reading a payload runs clean and processes an empty record. The warning says to check the record rather than trusting the failure path, since a parse that did nothing does not report one.
- Added `xml <text> processing { element "ID" into account.id; } on error { ... };` — `XML PARSE`. COBOL's XML reader is event-driven in Enterprise COBOL and GnuCOBOL alike: it calls a procedure once per token of the document and the procedure works out what to keep from the `XML-EVENT` and `XML-TEXT` special registers. There is no form that fills a record, so there is no `xml ... into ...` (`BANK-TYPE-026`); what there is says which elements go where, and the compiler writes the state machine. It gets the three things a hand-written handler gets wrong: it remembers the element a start tag opened, because the content arrives as a separate event; it forgets it at the end tag, or a parent's whitespace is filed under the child that just closed; and it converts a number through `NUMVAL` rather than `MOVE`, because moving characters into a numeric picture reads the digits positionally and puts the decimal point somewhere else. The handler is a section after the last `GOBACK`, since one in the flow of control would be run again on the way past. Bindings must name at least one element, must not bind one twice, and must read into a `string<n>` or a number.
- The `XML PARSE` caveat is the strongest in the compiler, and `BANK-TYPE-025` says so: GnuCOBOL compiles the statement and its registers, warns that it is not implemented, and then does nothing — no field filled, and neither the exception nor the not-exception branch taken, so a document that failed looks exactly like one that worked. What the local build does establish is that the COBOL is accepted: the handler is a section in the right place, the registers are the ones COBOL defines, and the conversions are legal. A test asserts `cobc` reports nothing but the pending warning.
- Added `report`, which becomes COBOL's Report Writer: an `RD` in the REPORT SECTION, `REPORT IS` on the `FD`, and the `initiate` / `generate` / `terminate` statements that drive it. `page ... footing ...` on a file paginates, but the program still writes every line itself and counts nothing; a report declares the shape and lets the compiler run it — headings repeated on each page, a footing at each change of a control field, and totals that accumulate without a variable to forget to clear. That last part is the reason to have it: a hand-written subtotal reset in the wrong place is a report that is wrong and still balances, which is the kind of defect that survives review. Groups are `pageHeading`, `pageFooting`, `detail`, `controlHeading`, and `controlFooting`; a column prints a literal, a field, `sum` of a field, or `pageNumber`. A field is named bare and resolved against the record the report's file holds, because a report is declared at the top level where no transaction's variables are in scope. Amounts print in their edited form with the picture taken from the field's own precision and scale, which is what lets a `COMP-3` balance reach a page at all. The names have to resolve or the COBOL means nothing (`BANK-FILE-008`), and a report's file is `sequential output` and may not also declare a page depth, since both decide where the page ends (`BANK-FILE-007`). The tests run a report and read the printed page back: heading, page number, per-branch subtotals, and a final total, none of which the source computes.
- Added `json <target> from <record> count <length> on error { ... };` and its `xml` twin — COBOL `JSON GENERATE` and `XML GENERATE`. A batch that has to hand a record to something outside the estate, a queue or a gateway or a file a distributed system reads, otherwise builds the text by hand with `STRING`, which is where the quoting and the escaping go wrong. COBOL builds the document from the group's own field names, so nothing in the language describes the shape: the record is the schema. `count` is the length actually generated, and it matters because the target is a fixed COBOL field that the compiler space-fills — without it the caller cannot tell the text from the padding. Both `count` and `on error` are optional, `from` and `count` stay usable as field names, and the failure handler is ordinary code the banking checks see into. The tests run the generated program and read the document back rather than only reading the emitted COBOL.
- A record carrying a `sensitive` field cannot be generated as JSON or XML (`BANK-AUD-002`). Serialised text is data on its way out of the program, so a card number in a payload is the same escape the rule already covers for an audit event and a log line — and the one most likely to be written by accident, since nothing in `json message.body from card;` mentions the field.
- Added `national<n>`, which emits `PIC N(n) USAGE NATIONAL`. The length counts characters and Enterprise COBOL holds each in two bytes of UTF-16, so the field occupies `2n` and every field after it is placed accordingly — which is the entire reason the type exists, since a mainframe record containing one does not line up if the field is counted as `n`. It is a storage type rather than a text type: a national may be assigned from, compared with, and passed as another national, and read from and written to files, but it does not mix with `string<n>` in either direction, literals included. Converting between them needs `NATIONAL-OF` or `DISPLAY-OF`, which GnuCOBOL does not implement, so rather than emit a move whose bytes differ between compilers the compiler declines.
- **A national field is the one thing this compiler emits that its own validation does not cover, and it now says so** (`BANK-TYPE-024`, a warning on every such field). GnuCOBOL 3.2.0 allocates four bytes per national character inside a group where Enterprise COBOL allocates two — measured, not assumed, with the reproduction recorded in `zos/README.md` — so under the local validator every field after a national sits at a different offset. It allocates two for the same picture at the 01 level, which makes it an inconsistency there rather than a rule, and warns on every such line that its handling of `USAGE NATIONAL` is unfinished. The compiler emits the Enterprise COBOL width because Enterprise COBOL is the backend it targets; the warning exists so the local evidence cannot be mistaken for a check that happened.
- Added `renames`, the level-66 regrouping. A legacy copybook splits a date into year, month, and day and then wants to move all three at once; `RENAMES` gives that run a second name without a second copy of the storage, which is what distinguishes it from `redefines` — a new _reading_ of the same bytes. The name reads as the alphanumeric span it covers, which is what a COBOL group move treats it as, so it is usable rather than merely declared. Both ends are qualified by the group in the generated code, because the same record is emitted in working storage and again inside every `FD` that holds it. Both ends have to be fields of the record, the first before the last, and the run cannot cross a table whose length depends on a count (`BANK-COPY-004`).
- Report two transaction parameters of the same record type (`BANK-TYPE-022`). A transaction is a program entry point, so its record parameters live in working storage — one COBOL group per record type — and two of a type were two names for one piece of storage: `a.value = 1; b.value = 2;` compiled to two writes of the same field, and the program silently disagreed with its source. A function is unaffected, since its record parameters are `LINKAGE` cells the caller rebinds.
- Added report pagination: `page <lines> footing <n> top <n> bottom <n>` on a file emits `LINAGE`, `advancing <n>` and `advancing page` emit `AFTER ADVANCING`, and `on page { ... }` emits `AT END-OF-PAGE`. This is how a COBOL report paginates — the compiler counts the lines and signals end of page at the footing, which is where a program writes its carried-forward total and the next heading. Without it a statement run is one unbroken column of text. A page depth belongs to a `sequential output` file and its footing has to be a line the page has; `on page` needs a declared depth, since otherwise there is no page to reach the end of (`BANK-FILE-007`). The end-of-page body is ordinary code, and the banking checks see into it.
- Fixed generated copybooks, which were a flat list of pictures rather than the record's own declaration: they dropped `REDEFINES`, `OCCURS` and its index, `SYNCHRONIZED`, nested groups, and the 88-levels of an enum. Under `copybookMode: "copy"` the program's storage _is_ the copybook, so those omissions were not cosmetic — a redefining field took storage of its own and pushed every later field along, a table collapsed to a single element, and an aligned field lost the slack bytes the layout report accounts for. Two `renderCopybook` implementations had drifted apart; there is now one, going through the same emitter the program does, and one place where a field's clauses are gathered. `bankc copybook inspect` reads the richer structure, so its offsets and the layout report's agree, and a test asserts they do.
- Added `justified` and `blankWhenZero`. `JUSTIFIED RIGHT` reverses COBOL's left-aligned alphanumeric move, which is how a code lands in the right of a fixed column without the program counting spaces; `BLANK WHEN ZERO` is how a statement line with no movement prints blank rather than `0.00`, said in the record rather than in a conditional. Both are checked against what COBOL allows them on (`BANK-COPY-005`), and may be written in any order with `sync`.
- Added sort input and output procedures. `USING`/`GIVING` lets the sort handle the files itself, which is right when the ordering is the only thing changing; a real batch program filters its input or totals its output on the way through, and could not say so before. A procedure replaces the clause it stands in for, and either may be given alone. The record it works through is an ordinary record variable, so the body reads and assigns fields as the rest of the program does; only the loop is generated — the `OPEN`, the `READ` or `RETURN`, the end-of-data test, and the `CLOSE`. Hand-writing those is where the shape is usually got wrong, since a `RETURN` whose `AT END` is forgotten reads the last record forever. `release` is what an input procedure exists for: the records it does not release are the ones it filters out. Writing it where no sort is running, an input procedure that never reaches one, and an input procedure on a `merge` are all `BANK-FILE-006`. The procedures are emitted as sections after the last `GOBACK`, because a section in the flow of control would be run again on the way past.
- Added alternate record keys, and the `DECIMAL-POINT IS COMMA` and `CURRENCY SIGN` conventions as project settings. A KSDS is browsed by its alternates, so a program that could only name the primary key could not open a file whose alternate index is the whole reason it exists; each alternate is declared `WITH DUPLICATES`, which is nearly always why one exists. The comma convention swaps the roles of the comma and the point inside pictures too, so edited pictures are rewritten to match — a picture built the other way round is not merely printed oddly, the COBOL compiler rejects it. A currency sign must be a single ASCII character a picture does not already use, which is checked when the configuration is read rather than producing a program the compiler refuses.
- Added `on error <file> { ... }`, which becomes COBOL `DECLARATIVES` and a `USE AFTER STANDARD ERROR` procedure. A file status check covers the statement that thought to look; this covers the ones that did not, whatever the operation and wherever it was written, which is what makes it the standard error path rather than a convenience. The handler is declared at the top level because it is not reached from a transaction — it runs when the failure happens — and it sees the file statuses and nothing else. A file may have one handler, which is what COBOL allows, and when any handler exists the program's paragraphs move into a section because everything after `DECLARATIVES` has to be in one.
- Added `log`, `accept`, and `reset` — `DISPLAY UPON SYSOUT`, `ACCEPT FROM SYSIN`/`DATE`/`TIME`, and `INITIALIZE`. The job log is the operator's only view of what happened between the return code and an abend, and a job parameter is how the same program runs a different cycle; a batch with neither is a black box. A restricted value may not be written to the log, for the same reason it may not reach an audit event.
- Added `sync` and `native<n>`. `SYNCHRONIZED` is the one layout clause that moves every later field without appearing in any field's own length: the compiler inserts slack bytes to reach the boundary, so a copybook that uses it and a reader that ignores it disagree silently, and every field after the first aligned one is read from the wrong place. The layout report now accounts for the slack and counts it in the record's length. `native<n>` is `COMP-5`, which holds the full range its storage can express rather than truncating to the picture's decimal digits — what an interface outside COBOL needs, and what the SQLCA already used.
- Added `zos/` and `pnpm zos:kit`, which writes every generated program, copybook, and job into the eight-character member names the JCL already expects, with a procedure and a results template. Nothing in it has been run: no BankLang program has been compiled by IBM Enterprise COBOL, precompiled by DSNHPC, bound, or started in a CICS region, and this does not change that. What it changes is that closing the gap is now a bounded afternoon for someone with access rather than an open question — including a list of the places GnuCOBOL and Enterprise COBOL most plausibly disagree, so a run knows what to look at.
- Added `sort` and `merge`, and `checkpoint` with the restart rule `BANK-FILE-003` was reserved for. A sort runs through a sort-work file described by `SD` rather than `FD`, and the generated job allocates `SORTWK01` for it; every file a sort touches must hold the same record, and every key must be a field of it, because a key that is not in the record sorts on nothing. A checkpoint writes the restart position and then commits, in that order, so a restart that finds a position can trust everything up to it is durable. A transaction that posts to the ledger inside a loop with no checkpoint is now warned about: a job that dies at row 3000 of 5000 and is rerun posts the first 3000 twice. It is a warning rather than an error because the compiler can see the hazard but cannot tell whether the job is rerunnable another way.
- Added `countOf` and `replaceChars` (`INSPECT`), `split` (`UNSTRING`), and `search` (`SEARCH`) — the three the string and table work had left out. Each does something a program could previously only fake: counting or replacing characters without a loop, taking a composite key apart, and finding a row without walking the whole table. `replaceChars` converts character by character, so the two sets must be the same size; anything else is a substitution, which COBOL has no single statement for. A `search` requires its not-found branch rather than offering it, because `AT END` is the half a hand-written scan usually forgets. Every `OCCURS` now carries an `INDEXED BY`, which is what `SEARCH` walks and is the idiomatic declaration anyway, and the index is reset before each search because `SEARCH` begins wherever it was left pointing.
- Added `redefines` and `depending on`, the two clauses a real copybook is built on. The variant record is how a legacy layout says "this area means different things depending on the record type", and `OCCURS ... DEPENDING ON` is what makes a variable-length record variable; a compiler that expresses neither cannot describe most of an existing estate's data. A redefining field must be declared after what it redefines and be no longer, because COBOL gives it no storage of its own and a longer one reads past the end (`BANK-COPY-004`); the layout report shows it at the offset it shares and leaves the record's length unchanged. A depending clause needs a whole-number count declared before the table, which COBOL reads to decide the record's length.
- Added CICS file commands, temporary storage queues, and `returnTransid`. Three commands is not an online program: a real one reaches a dataset through the region rather than through COBOL file control, passes state through temporary storage, and ends its task naming what runs next, which is what makes a pseudo-conversation possible at all. A read or write names the key it addresses; a rewrite does not, because it updates the record the preceding read is holding. A queue command is ordinary work rather than a commit boundary, so unlike a syncpoint it is allowed inside a loop. `returnTransid` takes no `resp` — there is no response to come back to — and suppresses the automatic `EXEC CICS RETURN` that would otherwise follow it unreachably. BMS, `START`/`RETRIEVE`, channels, and `HANDLE ABEND` are not included and the reference says so.
- Added `returnCode = <n>;`, the step's condition code. It lands in COBOL's `RETURN-CODE` and reaches the job as the value the next step's `COND=` tests; without it every step reported success, and a job that found no records looked exactly like one that processed a million. The value must be a whole number in 0–4095, which is what `RETURN-CODE` holds. `SORT`, `MERGE`, and checkpoint/restart are not included and the reference says so.
- Added the unit of work and positioned update to the Db2 profile. `INSERT`, `UPDATE`, and `DELETE` already worked, because a `sql` declaration carries whatever statement was written; what was missing was the ability to end a unit of work and to update the row a cursor is sitting on. `commit;` and `rollback;` lower to `EXEC SQL COMMIT` and `EXEC SQL ROLLBACK`. Neither is allowed inside a `cics transaction`, which finally gives `BANK-SQL-004` — reserved from the start as "transaction commit ambiguity" — the meaning it was waiting for: CICS owns the syncpoint there and commits Db2's work along with everything else, so an `EXEC SQL COMMIT` is not merely redundant but rejected by Db2 at run time. `WHERE CURRENT OF <cursor>` now rewrites the cursor to its COBOL name, without which a positioned update refers to a cursor Db2 has never heard of.
- Added the rest of VSAM: `update` mode, `rewrite`, `delete`, and the `start` / `readNext` browse. With only `open`, `read`, `write`, and `close`, and files that were either input or output, a master file update — the archetypal batch program — could not be written at all. `update` opens I-O, so the same `OPEN` serves the read that finds a record and the rewrite that puts it back. An indexed file is now `ACCESS MODE IS DYNAMIC` rather than `RANDOM`, because it is both read by key and browsed and `RANDOM` allows only the first. `START` uses `KEY IS NOT LESS THAN`, which begins at the first record at or after the key — an exact match would make a browse from a partial key impossible. A `write` or `rewrite` to an indexed file now captures `INVALID KEY`, because a duplicate key is the failure a KSDS write actually has and it is otherwise silent. `BANK-FILE-005` reports an operation the declaration cannot support.
- Added string handling: `trim`, `upper`, `lower`, `substring`, `concat`, and `now`. Without these a program could not assemble a narrative, parse a composite key, or mask a card number — so the `sensitive` declassification rule, which treats a function call as the boundary, rested on a masking function that could only return a constant. `concat("************", substring(pan, 16, 4))` is now a real mask. Every result has a length the compiler can name, because a COBOL field has a fixed one: `substring` takes literal bounds and rejects a slice running past the end, and `concat` sums its arguments. A computed string pads into a wider field exactly as a written literal does, and will not truncate into a narrower one. `concat` and `now` lower to a `STRING` statement rather than appearing inline, clearing the target first because `STRING` leaves whatever was past the end alone. `now()` assembles a Db2 timestamp from `CURRENT-DATE`, whose hundredths are all the clock offers, so the last four digits of the microseconds are zeros rather than invented. `INSPECT`, `UNSTRING`, and `SEARCH` are not included and the reference says so.
- Added `copybookMode`, a project setting choosing whether record layouts are written into the generated program or copied into it. The compiler emitted `.cpy` files and then inlined every record anyway, so nothing ever copied them — in a real shop the copybook is the contract between programs, and a program that does not `COPY` it can drift from it silently, which is the defect the copybook exists to prevent. `inline` stays the default, because a self-contained artifact is what the playground shows and what a reviewer reads on its own. `copy` emits `COPY <NAME>.`, adds a `SYSLIB` to the generated job's compile step, and puts the copybook directory on the local validation compiler's search path, so the mode that ships is the mode that is checked.
- Added `binary<n>` and `zoned<p, s>` alongside packed `decimal<p, s>`. Every number the compiler emitted was `COMP-3`, which meant it could not represent — and therefore could not read — most fields in an existing estate's copybooks: the halfword counters, the fullword sequence numbers, and the zoned decimal that much legacy input arrives as. A binary field is held in the halfword, fullword, or doubleword that fits its digit count, the way IBM Enterprise COBOL allocates `COMP`, and more than eighteen digits is `BANK-TYPE-002`. Zoned decimal is one byte per digit with a separate sign, so the field reads as plain text. Usage is representation and not meaning: it takes no part in type compatibility, only in the picture and the byte count, and the layout report now names it.
- Added `edited<T, "style">`, the numeric-edited items a mainframe program uses to put a number in front of a person. An amount held as `COMP-3` cannot be printed, so a statement whose amounts have no rendering is not a statement. Six styles cover what banking actually uses — zero suppression, thousands grouping, a trailing minus, `CR` for a credit, asterisk cheque protection, and a slashed date — and the picture is generated from the value's own precision and scale rather than written out, so nobody counts `Z`s. Assignment into the field is the formatting step, which is what a COBOL `MOVE` into a numeric-edited item does; the compiler emits `MOVE` rather than `COMPUTE`, because COBOL rejects the latter. An edited field is a rendering and not a number: it cannot be read back as a value, compared, or computed with, which stops a report column becoming arithmetic input and losing the digits the editing removed. An unknown style is `BANK-TYPE-023` rather than a picture passed through unchecked.
- Added `date`, `time`, and `timestamp`, with the calendar arithmetic that goes with them: `today()`, `addDays(when, days)`, and `daysBetween(from, to)`. A date is stored as `PIC 9(8)` holding `YYYYMMDD`, the mainframe convention, chosen because in that layout ordinary numeric comparison is also chronological comparison; a timestamp is `PIC X(26)`, Db2's own host variable format. Dates are nominally typed, so one cannot be compared with an amount or with a plain integer that happens to have eight digits. The arithmetic lowers to the COBOL intrinsics that know the calendar — `CURRENT-DATE`, `INTEGER-OF-DATE`, `DATE-OF-INTEGER` — rather than to `+` on the stored digits, because thirty days after the 31st of January is the 2nd of March. The language reference had listed `date`, `time`, `timestamp`, `int<n>`, and `uint<n>` as supported since the first release; three of them now are, and the two integer types have been removed from the list rather than left as a claim the compiler rejects.
- Added `sensitive` as a record field modifier, and the checks that make it mean something. A value marked sensitive may not reach an audit event or a ledger posting (`BANK-AUD-002`) — both are durable records that outlive the transaction and are read by people with no business seeing a card number — and may not be assigned to a field that is not itself marked (`BANK-SEC-001`), because a field's marking is part of its copybook and copying restricted data into an unmarked field would reclassify it silently. The check follows a value through locals. It deliberately does not follow one across a function call: that is the declassification point, made explicit rather than hidden, because following taint across a call needs per-function summaries and a language with no closures can express masking no other way. The copybook layout report now marks which fields carry restricted data, so an auditor reading the evidence does not have to read the source. `BANK-AUD-002` was reserved from the start; this is what it turned out to mean.
- Added Db2 cursors: `cursor <name>(...): <Record> { SELECT ... }` declares one, and `for each <row> in <cursor>(...) limit <n> { ... }` reads it. The `OPEN` and the `CLOSE` are generated around the body rather than written, so a cursor cannot be left open — a cursor still holding Db2 locks at the end of a batch window is a defect the language can make unwritable rather than diagnose. The bound is mandatory for the reason a `while` bound is (`BANK-TXN-004`), and the loop leaves on any non-zero `SQLCODE` rather than only on 100, because an error treated as end-of-data processes a partial result set as though it were the whole one. `DECLARE CURSOR` may not carry an `INTO`, so the author writes it on the SELECT where the query reads best and the compiler moves it to the `FETCH`; a cursor with no result record or no `INTO` is `BANK-SQL-006`. Confusing a cursor with a single-row statement is `BANK-SQL-005`.
- Added `examples/branch-accrual-cursor`, a batch Db2 program that reads a branch through a cursor and accrues interest, executed against the reference runtime in four scripted shapes: rows then end-of-data, no rows at all, rows that never run out, and an error mid-stream.
- Added record inheritance with `extends`. Base fields are laid out first, so a derived record's leading storage is the base record's storage byte for byte and an existing copybook for the base still reads a derived record. A derived record may be passed where the base is expected: a function's record parameter is a `LINKAGE` cell the caller points at the argument with `SET ADDRESS OF`, so the callee reads the derived record's own storage at the offsets `extends` guarantees. An argument with no address the caller can take — a subscripted element — is still `BANK-TYPE-021`. Cycles are `BANK-TYPE-016` and redeclared inherited fields are `BANK-TYPE-017`.
- Added generics on records and functions, monomorphised at compile time. COBOL has no boxing and no runtime polymorphism, so every instantiation expands into a concrete record or paragraph. Type arguments are normalised through the resolver before they name an instantiation, so `Slot<Money>` and `Slot<currency<"BDT", 18, 2>>` share one record. Generic functions infer their type arguments from the argument types, because `f<T>(x)` cannot be told apart from two comparisons without unbounded lookahead. New diagnostics: `BANK-TYPE-014`, `BANK-TYPE-015`, `BANK-TYPE-018`, `BANK-TYPE-019`, `BANK-TYPE-020`.
- Instantiated functions that lower to identical COBOL now share one paragraph. `larger<currency<"BDT", 18, 2>>` and `larger<currency<"USD", 18, 2>>` both emit `PIC S9(16)V99 COMP-3`, so emitting both was the same paragraph and the same storage twice. Sharing runs to a fixpoint, because two instantiations of a caller differ only in the callee they name until those callees merge, and the surviving name is the alphabetically first of the group so it does not depend on instantiation order. This changes what is emitted and not what is accepted: currency stays nominally typed, and a function the author named is never merged.
- The reference Db2 and CICS runtimes now report outcomes a test scripts, instead of always reporting success. `DSNHLI` receives the statement descriptor Db2 numbers its statements with, and `DFHEI1` receives the command name and returns its response in `EIBRESP` the way CICS does, with the translator emitting the `MOVE EIBRESP TO ...` that a `RESP` option asks for. A test seeding `SQLCODE 100` or `PGMIDERR` now executes the branch a generated program guards with `sqlcode == 0` or a `resp` test, rather than reading it out of the emitted COBOL. Every such value is still written down by the test: it says what the generated program does, not what Db2 or CICS would return.
- Added a failure model: `raise "CODE"` abandons the body, and an `on failure` block on a transaction handles it. It lowers to `BANK-FAILURE-CODE` plus a `GO TO` the body's exit paragraph, with the wrapper performing the body `THRU` that paragraph — a `GO TO` out of a plain `PERFORM` range leaves the flow of control undefined. Failures cross `PERFORM` boundaries because the caller tests the code, and cross `CALL` boundaries because the field is `EXTERNAL`. `if <bad> { raise "..."; }` is a guard clause needing no `else`. Handlers may not raise (`BANK-TXN-009`), and codes must fit `PIC X(32)` (`BANK-TXN-008`).
- A transaction that posted to the ledger now calls `BANKLEDG` with `ROLLBK` on its failure path, before the handler runs. BankLang does not own the ledger, so it delegates rather than generating compensating postings of its own.
- Added `entry transaction`. COBOL enters a program at the first statement of the `PROCEDURE DIVISION`, which previously meant whichever declaration happened to be emitted first — usually a helper function. The backend now emits a `BANK-MAIN` paragraph that performs the designated transaction, defaulting to the first declared one. Two entry points is `BANK-TXN-010`.
- Added a reference runtime in `runtime/`: `BANKLEDG`, `BANKAUDT`, `DSNHLI`, and `DFHEI1`. These satisfy the interfaces generated code calls out to, so a generated program can be executed rather than only compiled. They are small COBOL programs in this repository and imply no IBM behaviour; `runtime/README.md` states exactly what running against them does and does not establish.
- Added `tests/conformance.test.ts` and `tools/conformance.ts`, which compile a BankTS program, link it against the reference runtime, run it against seeded packed-decimal input, and assert on the ledger journal, the closing balances, the audit log, and the output records. Record layouts come from the compiler's own layout report rather than hand-counted offsets.
- Added `examples/withdrawal-with-recovery`, the first example that is executed rather than only compiled.
- Ledger postings now accept `currency` amounts. Previously only plain `decimal` was allowed, which made every currency-typed balance unpostable and defeated the purpose of having currency types.

### Fixed

- **A `split` that found fewer parts than it had receivers left the last one holding the previous record's value.** `UNSTRING` stops "when all the characters in the sending field have been transferred", and nothing in the statement clears a receiver it never reaches — so the field keeps whatever was in it. The overflow direction was already handled; this is the other one, and in a read loop it is the worse of the two, because the stale value belongs to a record the program has already finished with. Splitting `AAA-BBB-CCC` and then `XXX-YYY` into three fields left the third reading `CCC`: a value the program believes it just filled, in a field it did fill on the previous record, with nothing to distinguish the two. The receivers are now cleared to spaces before the `UNSTRING`, which is what an unfilled `string<n>` means. Verified by execution — the third field read `CCC` before and reads blank now.
- **`copybookMode: "copy"` emitted a `COPY` that no z/OS library could resolve.** The statement named the record's COBOL name — `COPY ACCOUNT-RECORD.` — while the bundle shipped that copybook as the member `ACCOUNTR`. Two rules, derived in different places, that never met. The Language Reference is precise about which one matters: "when the compiler searches for COPY members in PDS or PDSE datasets ... **only the first eight characters of text-name are used as the identifying name**". So on a PDS the compiler looked for a member called `ACCOUNT-`, which is neither eight characters of the right kind nor a name any library can hold, and `copy` mode had therefore never worked on z/OS. One rule now, `copybookMemberName`, used by whatever writes the member and by whatever writes the `COPY` that reads it.
- **Two records could share one copybook member, and nothing said so.** A member name is eight characters with the hyphens removed, so `AccountRecord` and `AccountRow` are both `ACCOUNTR`, and `EnquiryRequest` and `EnquiryReply` are both `ENQUIRYR`. One copybook overwrites the other in the library and every program that copies either gets a record with the name it asked for and different fields at different offsets — the one failure a copybook exists to prevent. `BANK-COPY-007` now reports it within a program. Four of the ten examples were affected and have been renamed; the records involved were genuinely different, including two examples that each declared a `TransferRequest` with different fields and two that each declared a different `InterestAccount`.
- **The z/OS bundle silently shipped a library six members short, and a manifest that said otherwise.** Every folder uploads to one PDS, so a name written twice is a member overwritten — the bundle wrote 22 copybooks into 16 files and then listed all 22 as if they had shipped. It now writes each name once, lists what actually shipped, and refuses to build at all when two _different_ members would collide rather than putting one under the other's name. The same record shared by two programs is written once and is nothing to report.
- **The bundle's manifest described the artifact it ships as something it is not.** It said "The generated JCL is free-format COBOL ... earlier releases need fixed format, which this compiler does not emit" — three things wrong in one sentence: JCL is not COBOL, the output has been fixed reference format since the emitter started writing it, and that is exactly what the sentence said the compiler does not produce. Anyone following it would have set the free-format option on fixed-format source, which reads the six blank columns every line begins with as code. The manifest now states the format the bundle actually contains and how a copybook member is named.
- **`DECIMAL-POINT IS COMMA` swapped the pictures and not the literals, so any program using it failed to compile.** The Language Reference describes the clause as exchanging "the functions of the period and the comma in PICTURE character-strings **and in numeric literals**", and only the first half was done. Under the comma convention a period in the source is a sentence terminator, so `COMPUTE BALANCE OF ACCT = 1234.50` parsed as a `COMPUTE` of 1234 followed by a statement called `50` — which is exactly what cobc reported: `unknown statement '50'`. The convention was declared, documented and tested for the picture it produces, and unusable for any program that wrote a decimal. Numeric literals are now written in the program's own convention, and only actual numbers are touched: the same clause carries string literals and enum member spellings, where a point is a character of the value. Verified by execution — 1234,50 plus 10,25 prints 1244,75.
- **A failure inside a nested function reported itself and let the step succeed anyway.** Every guard the compiler emits ends with `MOVE 12 TO RETURN-CODE` and `GOBACK`, which in the outermost program returns to the operating system and ends the job. In a _contained_ program `GOBACK` returns to the container, which carries straight on — and then overwrites the return code with its own on the way out. So an arithmetic overflow inside a `nested function` printed `ARITHMETIC OVERFLOW`, left the result field unset, let the caller use it, and ended the step with return code **zero**. The same held for the subscript guard, the `OCCURS DEPENDING ON` guard, the file status checks and the MQ checks — every failure path there was advisory. Inside a contained or recursive program the guards now end the run unit with `STOP RUN`, which terminates it from anywhere; the outermost program keeps its `GOBACK`, which reaches the same place, so the ordinary path is unchanged. Verified by execution: the same program printed a zero total and exited 0 before, and now names the field and exits 12.
- **Every program using a `nested function` reported `BANK-GEN-006`, unless the function's name happened to be one word.** A contained program is a program, so its source map entry has to anchor to the `PROGRAM-ID` — eight characters with the hyphens taken out — rather than to a paragraph name. The check handled the recursive case and not the nested one, so a function called `addUp` was anchored to `ADD-UP` while the program it became was `ADDUP` and its paragraph `ADD-UP-BODY`, and nothing in its lines carried the bare name. The suite did not notice because its one fixture is called `accrued`: a single word has no hyphens to take out, the two spellings coincide, and the entry anchored by luck. Any name written the way the rest of the language writes names did not, which is to say the feature reported an error on almost every real use of it.
- **An enum field was tested by comparing its member's spelling as a literal.** The level-88 conditions generated beside every enum field were used to _set_ it — `SET STATUS-CLOSED OF ACCOUNT TO TRUE` — and then the test next to it read `IF STATUS OF ACCOUNT = "CLOSED"`, which is the construct the 88 exists to replace. A condition name says which state is being asked about; a string comparison repeats the spelling in the procedure division, where it has to be kept in step with the 88 by hand. `!=` becomes `NOT <condition>`, which is how COBOL negates a condition name, and two enum fields compared with each other keep an ordinary comparison, there being no single condition to name.
- **A numeric field wider than eighteen digits was accepted and emitted a PICTURE Enterprise COBOL rejects.** The compiler bounded precision only for `binary`, and the hint on that check said in as many words that "packed decimal has no such limit here" — which is not true of the target. Enterprise COBOL's compiler limits give "PICTURE clause, numeric item digit positions: with ARITH(COMPAT) 18, with ARITH(EXTEND) 31", and the generated jobs pass no `ARITH` option, so eighteen is the ceiling and it applies whatever the usage. `decimal<25, 2>` emitted `PIC S9(23)V99 COMP-3` and `decimal<40, 2>` emitted thirty-eight digit positions; both compiled here and neither would compile on z/OS. Worse, `currency<"BDT", 40, 2>` reached the emitter with no validation at all — the currency type never went through the decimal checks, so it escaped the precision bound, the scale bound, and the integer check together. Both now share one validator, and the diagnostic states the real rule.
- **A record with an `OCCURS DEPENDING ON` used as a file record generated COBOL that no compiler accepts.** The `DEPENDING ON` clause named the count without qualification, and the record it belongs to is laid out twice — once in working storage and once inside the `FD` — so the name exists twice and both Enterprise COBOL and GnuCOBOL reject it: "'LINE-COUNT' is ambiguous; needs qualification". A previous session recorded a related gap for `RECORD IS VARYING`, whose length field must live _outside_ the record and where the bare name is therefore right; a table's count is the opposite case, belonging in the same record — a header count followed by the table it counts — which is exactly why it needs qualifying. The Language Reference allows it: "All data-names used in the OCCURS clause can be qualified; they cannot be subscripted or indexed." Each clause is now qualified by its own group, so the FD copy depends on the FD's count and the working-storage copy on its own.
- **The object of an `OCCURS DEPENDING ON` was never range-checked, and it decides how long the record is.** The Language Reference is unambiguous — "The behavior is undefined if the value of the object is outside of the range integer-1 through integer-2" — because the count is what makes the group variable: a count of 500 on a table declared `OCCURS 1 TO 100` describes a record of 2,538 bytes where 538 were allocated, so every group move, write, or call passing that record runs off the end of it. Nothing checked it, and the place it is least controlled is the place it usually comes from: the count arrives inside the record read from the file, so its value is whatever the dataset held rather than anything the program worked out. The count is now checked wherever the record is filled — after an assignment and after a read — naming it in the job log and failing the step with 12. Verified by execution: a count of 500 and a count of 0 are both refused with return code 12, and a count of 5 runs untouched.
- **A `read` copied every occurrence of a variable-length table rather than the ones the record has.** The generated mapping loop ran to the declared maximum, so a batch whose count said five copied a hundred — reading occurrences six to a hundred from past the end of the data the `READ` delivered, which the standard leaves undefined. The loop is now bounded by the count, which is checked immediately before it.
- **A subscript was guarded only when it appeared in the value being assigned, so an out-of-range index on the _target_ wrote past the end of the table.** COBOL does not check subscripts: an index past the end addresses whatever storage follows, and inside a record that is the next field. `book.bands[at].cap = 999.00` with a ten-element table and `at` of 11 therefore assigned to `book.total`, the field declared after the table — which then held a value nothing in the program had assigned to it, with no diagnostic and a return code of zero. Guarding had been written as a switch over expression kinds, reached from one place, and it leaked at every seam: besides the assignment target, the subscripts in an `if` condition, in a `log`, in the arguments of the numeric, string, and temporal intrinsics, and in every statement inside a sort procedure were all unguarded. Guards are now collected by walking the statement's own data rather than by a list of contexts someone has to remember to extend, so a subscript is guarded because it is there — and a statement kind added later is covered without being thought about. A `while` condition is guarded twice, before the loop and at the end of the body, because it is evaluated again before every iteration and the body may have moved the index in between. Inside a sort procedure the guard cannot raise, control not being allowed to leave one while the sort is running, so it names the subscript, sets `SORT-RETURN` to 16, and brings the index inside the table so the guarded statement cannot corrupt the record on the way out. Verified by execution: the same program set a neighbouring field to 999.00 and exited 0 before, and now names the violation and exits 12, with the neighbour untouched.
- **A raise no handler caught ended the step with return code zero.** The failure paragraph rolled the ledger back and ran the program's `on failure` handler, and where there was no handler it did nothing at all — the body stopped where it failed, the wrapper returned, and the job reported the same success as a transaction that had finished its work. That is the shape of failure nobody investigates. An unhandled failure now names the code it raised in the job log and returns 12. A transaction that declares a handler is left alone: the handler is the program's stated recovery, and what it returns is the author's decision.
- **An arithmetic result too large for the field receiving it was silently truncated, and the truncation took the high-order digits.** No generated statement carried `ON SIZE ERROR`, and the Language Reference says exactly what COBOL then does: "If the ON SIZE ERROR phrase is not specified and a size error condition occurs, truncation rules apply and the value of the affected resultant identifier is computed." Because it is the leading digits that go, an overflow does not produce a number big enough to notice — it produces a plausible small one. Two amounts a field can each hold do not add up to one it can, and a bank's arithmetic is mostly additions of amounts of the same declared width, so this was the ordinary case rather than an exotic one: `decimal<9, 2>` receiving 9,999,999.99 + 9,999,999.99 stored **9,999,999.98**, ten million short, and the program exited zero. Every computation now carries the phrase, naming the field in the job log and returning 12, which is what the file status checks already did for a failed I/O. Stopping is safe precisely because COBOL leaves the receiving field alone when the phrase is present — the wrong value is never stored, so nothing downstream has read it. Division by zero raises the same condition and now takes the same path instead of ending the step abnormally with no indication of which computation did it. Naming a value cannot overflow the field it was declared for, so a plain assignment stays unguarded rather than carrying four lines of COBOL that can never run. The type system is deliberately not doing this work: giving `a + b` a type one digit wider than its operands would push the widening through every record in the program, and the values that matter are only known at run time. Verified by execution: the same program printed +9999999.98 and exited 0 before, and now names the field and exits 12.
- **Every report total was sized for one row, so a subtotal over a busy control break silently lost its high-order digit.** Report Writer takes the internal total field's precision from the picture on the `SUM` entry, not from the field being totalled, whenever the item summed lives outside the REPORT SECTION — which here it always does, the values coming from the record in working storage. The Report Writer Precompiler manual is explicit that the widening rule is the other way round ("If the SUM clause refers to a REPORT SECTION item, the precision of the total field is increased if necessary"), and it flags the hazard itself: "It may be difficult to estimate the number of digits needed for totals, since this will depend on the number and content of items to be accumulated." The compiler was printing each total with the picture of the row it totalled, so a `decimal<9, 2>` amount got a seven-digit accumulator: two postings of 9,999,999.99 subtotalled **9,999,999.98** instead of 19,999,999.98, and a run of three totalled 9,999,999.97 instead of 29,999,999.97. Nothing reported it. The detail lines are right, every footing is internally consistent with the truncated figures above it, the step ends with return code zero, and the only way to find it is to add the report up by hand. On z/OS the default `SUM OVERFLOW PROCEDURE IS STANDARD` makes it worse in a different direction — the addition is _discarded_ rather than truncated, so the total stops where the last one that fitted left it. A total now gets all eighteen digits `ARITH(COMPAT)` carries, with the operand's own scale, which no number of rows a program can read will overflow; there is no honest way to derive a narrower one, because how large a total gets depends on how many rows arrive and that is not known until the job runs. Verified by execution: the same program printed 9,999,999.98 before and 19,999,999.98 after.
- **The executed report test proved less than it looked like it did.** GnuCOBOL 3.2.0's Report Writer reads a `COMP-3` operand of a `SUM` clause from the wrong place, picking up only its low-order digits — an amount of 1,000,000.00 totals as **zero**, one of 9,999,999.99 totals as 999.99, while the same field read by `SOURCE` on the line above prints correctly. Money is `COMP-3` in every generated program, so under the local validator every total in every report is wrong. The suite did not notice because its fixture used 42.50, which is small enough to survive the truncation and come out right by luck: a green executed test that appeared to prove totals work, and proved nothing of the sort. It reproduces in a hand-written program with no BankLang involved, two fields of the same value and picture differing only in `USAGE`. The pagination test now asserts the shape of the report rather than its figures, a new test proves the totals themselves over a `zoned` amount, which GnuCOBOL accumulates correctly, and a third pins the divergence so it fails if GnuCOBOL ever fixes it. `zos/README.md` records it, and report totals are named there as the first thing to check on the mainframe.
- **`sum` of a string was accepted and emitted `PIC X(6) SUM ...`.** A `SUM` clause accumulates with `ADD`, so its operand has to be numeric; the compiler took whatever field was named and built the total's picture from it, producing a report description the Report Writer Precompiler rejects. `BANK-FILE-008` now requires a `decimal` or a currency amount. The same diagnostic's rule about _where_ a `sum` may go was stated as though COBOL required it — Report Writer in fact allows a `SUM` clause in a group of any type, including a heading. Confining it to a footing is a banklang rule, made because a total read before the details it covers is a figure no reader can check, and the diagnostic and the language reference now say that rather than asserting a restriction COBOL does not have.
- **`returnCode = 8` reached the operating system as zero.** `RETURN-CODE` is a shared special register, and the Language Reference is explicit about what a call does to it: "the RETURN-CODE special register in the calling program is set to the value of the RETURN-CODE special register in the called program". Every generated transaction ends by calling `BANKAUDT`, so a return code set anywhere before that — which is anywhere at all — was overwritten with the audit program's zero. A batch that detected a bad condition, said so, and finished normally reported success to the scheduler, and every `COND=(4,LT)` step after it ran on that basis. The value is now held in `BANK-RETURN-CODE` in working storage and moved into `RETURN-CODE` as the last thing before the program leaves, after the final call. The failure paths are unchanged: each sets `RETURN-CODE` and returns with nothing in between, so there is nothing left to overwrite it. Verified by running a generated program under GnuCOBOL: before, exit status 0; now, 8.
- **A `split` that ran out of receivers dropped the rest of the field silently.** `UNSTRING` raises the overflow condition when every receiver has been filled and the sending field still has characters nobody looked at, and the statement carried no `ON OVERFLOW` phrase — so a reference split into two when it had three parts left the third nowhere and the program carried on holding a prefix of the value it was given. The phrase is now emitted: it names the field in the job log and sets a return code of 4, never downwards, since taking the leading parts of a longer field is something a program may mean to do but is not the ordinary run.
- **A program with a `report` was given a job that could not compile it.** Report Writer is not part of Enterprise COBOL. The Language Reference states that the Report Writer module "is supported with the optional IBM COBOL Report Writer Precompiler and Libraries (5798-DYR)" and lists `RD`, `PAGE LIMIT`, `CONTROL HEADING`, `PAGE FOOTING`, `SUM`, `COLUMN` and report description entries as features that precompiler supplies — so a `REPORT SECTION` handed straight to `IGYCRCTL`, which is what the generated JCL did, fails at the compile step. The reason it went unnoticed is that GnuCOBOL implements Report Writer natively: the executed tests pass, and the local target needs no such step, so every piece of local evidence said the feature worked. The job now runs the stand-alone precompiler `SPCRWCOB` first — `SYSIN` in, `RWWORK` for working space, `SYSINS` out, and the compile step reading what it wrote — and the link-edit step picks up the Report Writer run time library, which the expansion leaves external references to. It runs before the CICS translator and the Db2 precompiler, since Report Writer passes `EXEC ... END-EXEC` through unchanged and neither of the others understands a `REPORT SECTION`. Step order and DD names are from the precompiler's own Installation and Operation manual, and `docs/language-reference.md` now says what a report costs an installation that has not licensed 5798-DYR.
- **A field declared after a `depending on` table was given an offset it only has when the table is full.** Anything following a varying table is _variably located_: it sits at the start of the table plus the count times the entry, so it moves every time the count does. The layout report and the copybook stated the maximum-count offset with nothing to say it was one value of many — a copybook naming a byte position that no record with a shorter table has. IBM calls this complex `ODO` and permits it; GnuCOBOL refuses it outright ("`LINES-FLD` cannot have OCCURS DEPENDING because of `IDEMPOTENCY-KEY`"), so a program built this way could not have been executed locally either, and the fixtures that used the shape had never been compiled. The varying table now has to be the last field in the record that takes storage, which is where a variable-length record conventionally puts it, and `docs/diagnostics.md` records the narrowing and the reason.
- **Only `OPEN` tested the file status; every other I/O statement set one that nothing read.** IBM's guidance is to check the file status key after each input or output request, and `CLOSE`, `WRITE`, `REWRITE`, `DELETE`, `START` and both forms of `READ` were unchecked. The failure this hides is the quiet one: a `WRITE` that cannot happen — the volume full, a `varying` record outside its declared length range — leaves the loop running, the output file short by however many records were left, and the job ending with a return code of zero. A `CLOSE` that could not write its last buffer loses the records the program believes it wrote. A read that fails partway through a file ends the batch loop exactly as end of file does. Each statement is now followed by a test of the status **key**, not of `= "00"`: class 0 is successful completion and includes "02", "04", "05" and "07". The statuses a statement is written to produce are still the program's own — end of file on a read, a missing key on a keyed read or a browse, a duplicate key on a KSDS write — so a batch loop still ends the way it did. Inside a sort's input or output procedure the failure sets `SORT-RETURN` to 16 rather than returning, since control may not leave a sort procedure while the sort is running; the procedure's own generated `CLOSE` is now checked too. Verified by running a generated program that writes a record shorter than its declared minimum: before, GnuCOBOL did not write it and the program returned 0 with an empty output file; now it reports `WRITE FAILED feed STATUS 44` and returns 12.
- **No generated program was in COBOL reference format, so none of them could have compiled on z/OS.** Enterprise COBOL reads a 72-character line — columns 1-6 sequence number, 7 indicator, 8-11 Area A, 12-72 Area B — and there is no option on z/OS that widens it. Two things broke it. The generated-code banner started in column 1, which puts its fourth character in the indicator area: `invalid indicator 'e' at column 7`, on line 1 of every program and every copybook. And hundreds of lines ran past column 72, where nothing is truncated with a diagnostic — the compiler simply does not see the rest, so `ACCOUNT-INPUT-STATUS` arrives as `ACCOUNT-INPUT-S` and the compile fails on an undefined name that a reader looking at the source cannot find. A copybook was worse still: it was written with its `01` in column 1 on the reasoning that a copybook stands alone, but a copybook is source, read in the same reference format as the program that copies it. Every generated line now goes through a reference-format pass: a statement too wide is broken at a space and continued in Area B; a literal too wide is filled to column 72 _exactly_ — every column of a continued line through 72 is part of the literal, so stopping short pads the value with blanks — and reopened on a line carrying the hyphen in column 7; a comment continues as a comment. The columns a data description entry lines its pictures up in are preserved rather than reflowed. **JCL had the same defect**: fields end at column 71, and every JOB card ran past it, losing `NOTIFY=&SYSUID` — a job that names a program with a long name loses whatever the tail happened to be. Cards now continue after a complete parameter including its comma, resuming in column 16.
- **The local validator was proving nothing about the target.** Every `cobc` invocation in the repository passed `-free`, and GnuCOBOL reading a file whose first line starts in column 1 switches to free format on its own anyway — where no column means anything and no line has a margin. That is how ten examples and eighty test files stayed green against COBOL that the real compiler rejects at line 1. Everything is now `-fixed`, the example validator also passes `-Wcolumn-overflow`, and `tests/reference-format.test.ts` checks the margin, the indicator column and the sequence number area over every generated artifact — including an executed proof that a continued literal still holds its whole value after a round trip through `cobc`. The reference stubs in `runtime/` were reflowed to fit as well.
- **A `redefines` inside a group was laid out past the storage it aliases.** The top-level walker was fixed to carry the anchor; the recursion into a group's fields was not, so `companyName redefines personalName` at the top of a record reported offset 2 and the same two lines inside a group reported 42 — the offset of the byte after the forty it shares. Its neighbours were right, which is what makes it read as a layout rather than a bug: the copybook says the alternate reading of the name area starts where the branch code starts. All three walkers over these rules now share one implementation.
- **A redefinition longer than what it redefines was rejected**, and the reason given was wrong. Enterprise COBOL permits it: the redefinition extends the storage area rather than overrunning it, and the Language Reference's own example is `05 A PICTURE X(6).` redefined by `05 B REDEFINES A PICTURE N(4).` — eight bytes over six — with the note that B "can occupy more storage than the redefined item". The only case it forbids is a redefined item declared as an external data record, which this language cannot declare. The record now runs to the end of the longest reading of the area and the fields after it move by the overhang; the layout report, the copybook inspector, and the typechecker's own byte count all agree on where they land.
- **A `redefines` separated from what it redefines was accepted and emitted.** COBOL requires the readings of an area to follow its description with nothing in between that takes storage of its own, so `a; x; b redefines a` is not a program — Enterprise COBOL rejects it and GnuCOBOL says "REDEFINES must follow the original definition". The compiler emitted it anyway, and laid `b` out at `x`'s offset rather than `a`'s, so the copybook described the alternate reading in the wrong place as well. A further redefinition may still name either the original or the redefinition before it, which is how a third reading of one area is written.
- **A table could be redefined, and a redefinition could carry `depending on`.** COBOL allows neither: `OCCURS` cannot appear on a redefined item, because a table is a repetition of an area rather than one area to alias, and neither end of a redefinition may vary in length, because the area's size has to be known to lay out what follows. The compiler emitted `05 FLAT REDEFINES ROWS` over an `OCCURS` group, which GnuCOBOL warns on, and `05 ROWS REDEFINES A OCCURS 1 TO 3 TIMES DEPENDING ON CNT`, which it rejects outright as "cannot be variable length". Both are now `BANK-COPY-004`.
- **A `SORT` or `MERGE` never tested `SORT-RETURN`.** The sort product reports its outcome there — 0, or 16 for a sort that did not complete — and IBM's programming guide has always said to test it after every statement, because what a program does having ignored it is undefined. The concrete failure is quiet rather than loud: a sort whose input never opened releases no records, so the output file is written, is empty, and the job ends with a return code of zero, which is indistinguishable from a night when there was nothing to sort. The generated program now reports which file failed and what the sort returned, sets a return code of 16, and stops. Inside an input or output procedure the same failure sets `SORT-RETURN` to 16 instead, since control may not leave a sort procedure while the sort is running and the `GOBACK` used everywhere else is not available. A run under GnuCOBOL with the input dataset removed is what this is checked against: before, the same program wrote an empty output file and returned zero.
- **A checkpoint wrote a restart position that nothing could read back**, which leaves the rerun starting at the beginning exactly as it would with no checkpoint at all — and `BANK-FILE-003` told the programmer that adding the checkpoint had made the job safe to rerun. `restart <file> into <record> { ... } else { ... }` is the other half: a keyed read of the position, a branch for resuming from it and a branch for the first run. The warning now requires both halves, so it can no longer be silenced by the half that does nothing on its own. A restart file must be `indexed update`, because a sequential output file is rewritten from the start by the next `OPEN` — so a rerun that dies before its own first checkpoint destroys the position it was resuming from, and the run after that starts from the beginning. One keyed record, rewritten in place by each checkpoint, has no such window, and is what a restart control record on z/OS conventionally is. A restart file is generated `SELECT OPTIONAL`, since the first run has never written a position and the dataset does not exist yet. Verified by running a generated program three times under GnuCOBOL: the first reports nothing to resume, the second and third resume from the committed position.
- An `OPEN` that succeeded could still stop the job. The status test introduced with the check below was `NOT = "00"`, and "00" is not the only success: the first character of a file status is the status key, and 0 is successful completion. "05" is an `OPTIONAL` file that was not there and has been created — the ordinary first run of a batch that keeps a restart position — and "07" is a tape-oriented `CLOSE` option on a device that is not tape. GnuCOBOL returning 05 on the first run of a restartable batch is what surfaced it. The test is now on the status key.
- An `if` could not be written inside a `while` body (`BANK-TYPE-007`), though a `for each` body has always allowed one and a `switch` was permitted in both. That made a read-ahead loop — read, then act only if the read found something — impossible to write, and `examples/interest-posting-batch` had the bug it forces: the iteration that reaches end of file still runs its body, so its unguarded `write` appended one trailing record holding the previous one's values. What the diagnostic is for is keeping `return` out of a loop, which is unaffected.
- The generated job ran its later steps whether or not the earlier ones worked. Only `LKED` and `BIND` carried a `COND`, so a compile that failed left the link-edit and bind bypassed and the run step still executing — against whatever load module the library already held, which is the previous version, under a return code that says the job worked. Every step after the first is now bypassed on a failure.
- **A Db2 batch program was started with `EXEC PGM=`**, which gives it no thread to Db2 and fails on its first SQL statement. A Db2 program is run by the DSN command processor under TSO in batch: the run step is now `IKJEFT01` with `DSN SYSTEM(...)` and `RUN PROGRAM(...) PLAN(...) LIB(...)`. The job also bound a package and no plan, so there was nothing to run under even once the step was right; it now binds both.
- A new output dataset was catalogued whatever happened to the step. The abnormal disposition is the one that matters: a step that dies halfway through writing has produced a partial dataset, and cataloguing it invites the next job in the chain to read it as though it were a complete day. It is now `DISP=(NEW,CATLG,DELETE)`. A file declared `update` was given `DISP=(NEW,...)` as well, which would have allocated an empty dataset for a program that reads and rewrites one in place; it is now `DISP=OLD`.
- **The GnuCOBOL lane validated one example.** `pnpm test:gnucobol` ran against `account-transfer` and nothing else, so "validated against GnuCOBOL 3.2.0" meant one program out of ten. It now runs every example and prints each. Per-construct coverage was thinner still — it was whatever individual tests happened to invoke `cobc` for — so `tests/gnucobol-coverage.test.ts` now compiles one program per construct and fails on any error, and on any warning outside a named list of three. That list is the inventory of where the two targets genuinely diverge: `national`, `json ... into`, and `xml ... processing`, all of which GnuCOBOL 3.2.0 compiles and does not implement. A construct joining it should be a decision, not a surprise.
- A `varying ... length <field>` whose length field was declared inside the record it measures was accepted, and emitted `DEPENDING ON` against a name that resolves twice — the record is laid out in working storage and again inside the FD — which neither compiler takes. The depending item has to live outside the record whose length it gives; `cobc` says so directly if you try to qualify it the other way. Found by the coverage test above, on its first run.
- **A `sync`ed binary inside a table was ignored by the layout report entirely.** The clause was emitted, so IBM's compiler inserts the bytes; the report just did not know about them. It forces slack twice over — once before the item, and once at the end of every occurrence, because IBM divides the group's size by the largest boundary anything inside it demanded and pads the difference so occurrence two starts where occurrence one did. A ten-element table of a group holding one fullword was reported as 100 bytes where the dataset has 120, and every field after it was named at an offset the dataset does not have — which is the one number a layout report exists to give. Checked against IBM's own worked example from the Language Reference, whose published answer is a 16-byte occurrence and a 161-byte record; the compiler now agrees with it.
- **A `sync`ed binary field of ten digits or more was aligned on an eight-byte boundary, and Enterprise COBOL aligns it on four.** IBM's slack-byte algorithm divides the bytes so far by 2 for a binary item of four digits or fewer and by 4 for one of five or more — there is no 8 for a binary item, which belongs to `COMPUTATIONAL-2`. A `binary<18>` occupies eight bytes and still aligns on a fullword. The compiler was inserting slack IBM does not, so every field after such an item sat four bytes further along than the dataset has it, and the layout report said so with confidence. Nothing local could have shown this: GnuCOBOL was never being asked where IBM puts a field. The packed, binary, and zoned _sizes_ were checked at the same time and are right — packed matches IBM's formula for every width, and zoned is a byte per digit plus the separate sign the picture actually declares.
- A `rewrite` or `delete` on a sequentially accessed file was accepted with nothing read before it (`BANK-FILE-010`). Both replace the record the last `read` returned, so without one the operation is not performed and the status is 92 — no abend and no exception, so a program that does not test the status carries on believing it updated something. Indexed files are unaffected, being `ACCESS MODE IS DYNAMIC`, where the record key says which record is meant. A read in an enclosing block covers a branch inside it and a read inside a branch does not travel back out, which is the rule `BANK-DLI-002` already applies to a get-hold.
- A `delete` on a file with sequential organization was accepted (`BANK-FILE-011`). Enterprise COBOL has no `DELETE` for one: a record is removed by leaving it out of the file the next program writes. GnuCOBOL compiles the statement, so the generated program passed every local check and would have been rejected by `IGYCRCTL` — which is the whole reason the local validator is not the same thing as being right.
- **An XML element's content kept only its last fragment.** IBM is explicit that "splits in character content might occur at arbitrary points in the XML data stream, even with unsegmented input", and that the register signalling it "may be required for any and all attribute values and element character content" — so this is the parser's ordinary behaviour, not an edge case for large documents. The generated handler moved each `CONTENT-CHARACTERS` fragment straight into its field, so a value arriving in two pieces landed as the second piece alone: an account id of `ACC-000000000042` becomes `0042`, which is short, plausible, and silent. Fragments are now accumulated with `STRING ... WITH POINTER` and the field assigned only when `XML-INFORMATION` says the value is complete.
- A `JSON PARSE` reported through `on error` only, which catches one of its two failure modes. An exception condition terminates the statement and sets `JSON-CODE`; a **nonexception** condition does not terminate it, sets `JSON-STATUS`, and "might result in the receiver being partially modified" — so the statement completes, the handler is never entered, and the record holds some fields and not others, which is what a record that parsed cleanly looks like. A `JSON-STATUS` test now reports it. Reported rather than raised, because a nonexception condition is not always an error: a document carrying fields the record does not declare is one, and is often what was expected.
- The commarea guard tested only whether one was passed. IBM's rule is that the program verifies `EIBCALEN` matches what it expects, because a discrepancy risks a storage violation — and a caller passing ten bytes to a program whose record is seventy-two left the `MOVE` reading sixty-two bytes of whatever followed the commarea, which is somebody else's storage and reads clean. The test is now against the length of the record, which covers the short commarea and the absent one together.
- The I/O PCB mask stopped at the userid, describing eight of the twelve fields IMS puts there. In DB batch only the status code is populated, so the short mask read the status correctly and nothing noticed — but a PCB mask is a description of storage the region owns, and IMS's instruction is that it "must contain the same fields, in the same order". A description that omits the end stops being true the moment anything is added to it. The group name, the extended time stamp, and the userid indicator are now declared, the time stamp as bytes rather than numbers because its time is twelve packed digits carrying no sign and its UTC offset is four bits of attributes ahead of a packed value — neither is a COBOL numeric picture.
- The Db2 run step used `IKJEFT01`, under which a program that abends does not abend the step: TSO catches it and the step ends **normally** with condition code 12. A step that ended normally takes the normal disposition, so the `DELETE` added to every output dataset above would never be honoured and the half-written dataset would be catalogued after all. `IKJEFT1B` terminates the step with X'04C', which is what makes a conditional disposition mean anything. The bind step keeps `IKJEFT01` for the opposite reason: a `BIND` that only warns returns 4, and `IKJEFT1B` stops the moment anything returns non-zero, so the plan would go unbound because the package warned.
- A `SORT` or `MERGE` tested `SORT-RETURN` and not the file status keys, which is half of what IBM's table for this exact configuration calls for. Under `NOFASTSRT` the sort does not check open, close, or I/O errors on a `USING` or `GIVING` file, and the guidance for a program that declares a file status and no `ERROR` declarative — which is every program this compiler emits, since `BANK-FILE-001` requires the status — is to test the status key as well. The status was being set and nothing read it. Files a sort procedure opened are left alone, having been checked there.
- A sort-work file's `SELECT` assigned it to `SORTWK01`, conflating two different things that shared a name. COBOL requires the clause on an `SD` and then treats the name as documentation — IBM's example assigns two `SD` files to the same one — so nothing was allocated for it and no DD answered to it, while `SORTWK01` is the DD the sort product reads for its first _work dataset_, which the job separately allocates. It read as though the `SD` were bound to that dataset, and anyone who changed one to match the other would have found that neither mattered. The `SD` is now assigned to `SORTWORK`, and a test checks that two sorts in one program can share it.
- The run step had nowhere to write a dump, leaving the return code as the only evidence of an abend. `CEEDUMP` and `SYSUDUMP` are now allocated. Sort work datasets were one rather than the customary three, and were allocated for a `MERGE`, which needs none — its inputs already arrive in order, so there is nothing to spill. Whether the job needs them is now derived from the program by the emitter rather than declared by the caller, since the emitter has the program in hand and a job whose work datasets depend on a caller remembering to say so is a job that is missing them the first time someone forgets.
- `examples/account-file-batch` declared two files and a function and never opened, read, or wrote anything — an example named for something it did not do, which is part of why file I/O went unaudited as long as it did. It is now a sequential batch that reads every account, flags the overdrawn ones, and writes a posting record, with the guarded read-ahead the loop needs.
- An `OPEN` never tested the file status. The language has always required a file to declare one (`BANK-FILE-001`) and then generated nothing that read it, so a failed open carried straight on: every read after it fails too, and a batch that ignores that writes an empty output file and returns zero — which looks exactly like a run that had nothing to do. Convention is to check after every I/O and, for an open, to abort. The generated program now reports which file and what the status was, sets a return code of 12, and stops.
- **A CICS transaction never received its input.** The first record parameter is working storage and nothing moved `DFHCOMMAREA` into it, so the program read uninitialised bytes; nothing moved it back either, so a caller expecting updated data got whatever it sent. Both directions are now generated. Every test passed while this was broken, because the reference CICS runtime passes no commarea and the assertions were about which branch ran.
- A CICS transaction did not test `EIBCALEN` before addressing `DFHCOMMAREA`. A commarea that was not passed is not an empty record — it is storage belonging to something else, and reading it is a violation — so IBM's guidance is to test first, always. The program now abends with `BKNC` rather than continuing, because no commarea where one is required is a broken contract and returning quietly would make it look like the transaction ran.
- The generated EXEC interface block held two fields. It now carries the block a program actually reads, `EIBCALEN` included. Growing it exposed the matching defect in the reference CICS runtime, which described the old short layout in its own `LINKAGE` and therefore wrote `EIBRESP` at an offset the caller did not read — so a command that failed looked like one that worked. The two are now the same layout, and a test says why they have to be.
- Host variables were not inside an SQL declare section, which Db2 requires. The markers are declarations rather than statements, so the precompiler removes them the way Db2's does — translating one into a call put an executable statement in the DATA DIVISION, where none may appear.
- **A syntax error could hang the compiler instead of reporting one.** Each of the parser's four recovery routines stops on the token it wants to resume at; a parse that failed without consuming anything leaves that same token current, so the loop that called the recovery resumed exactly where it started and did it again forever. What the author saw was the compiler exhausting memory, which is the worst possible way to be told about a missing brace — and it was found by accident, while sweeping every reserved word through a field-name position. Recovery now either advances or the caller advances for it, so every iteration consumes at least one token and progress is structural rather than a property each routine has to remember to preserve. Across a sweep of 1,805 malformed sources — every truncation of a valid program, keywords injected at every boundary, and stray punctuation throughout — that guarantee has to force progress about two hundred times, and each of those was a hang. The sweep is now a test.
- A record with no closing brace parsed clean and reported nothing, silently becoming a record with fewer fields than it was written with: the field loop stops at the end of the source and could not tell that from reaching the `}`. It now says which record ran off the end.
- **Not one of the 81 reserved words could be used as a field name.** `type`, `date`, `currency`, `error`, `record`, `file`, `transaction`, `log`, `commit` — words that appear in nearly every real copybook — could not be declared or read at all, so a great many actual bank records could not be described in a language whose purpose is describing them. Making words contextual one at a time, as each collision was found, was a slow leak that only surfaced when somebody's copybook could not be expressed. A name being declared or selected is now allowed to be a keyword, which is sound because those positions cannot be anything else: a field name is followed by `:` and a member name follows `.`. `sensitive` is told apart from itself by the same rule — a marking when a name follows it, a name when a colon does. Parameters and locals are deliberately excluded: they are read as bare identifiers in expressions, where a keyword really is a keyword, so accepting one would allow a name that could be declared and never read. A test now round-trips every reserved word through a declaration, a read, and an assignment.
- An element of a scalar table could not be assigned to at all. `rates[1] = 0.05;` was reported as "not an assignable target", so such a table could be declared and read but never filled — which is not a table worth having, since a rate matrix loaded from a file is written a cell at a time. Only `rows[2].rate = ...`, a field of an element, happened to work, because that parses as a member access rather than an index. An index is now a place a value can go, at any depth.
- Every `bankc` command stopped on any diagnostic, so a warning was an error wearing a softer word. A batch warned about its restart hazard (`BANK-FILE-003`) could not pass `check`, be emitted, or be built, and the same would have been true of any program using a construct that merely carries a caveat. Commands now stop on errors; warnings are printed and the work goes ahead, including on the success path of `check` and `emit cobol`, so nothing is hidden by an exit code of 0.
- `bankc` copybook inspect and diff threw on the compiler's own output. The picture reader knew only `PIC X` and `COMP-3`, so every field the numeric-usage, temporal, and edited work added — a `binary`, a `zoned`, a date, an edited amount — made it fail, and nothing noticed because no example used one. It now measures every picture the emitter produces, with a test that lists them.
- The compiler halted on any diagnostic, so a warning produced no COBOL at all — a worse outcome than the thing being warned about, and the reason no warning had ever been useful. It now halts on errors, and warnings from every phase travel with a successful result rather than being dropped on the way out. That fix reached the compiler's own gates but not lowering, which kept its own "any diagnostic at all" guard, so the behaviour it described was never actually true: a program whose only complaint was an uninstantiated generic (`BANK-TYPE-015`) still compiled to nothing and came back `ok: false`, with a warning as the only explanation — and the warning says no COBOL is generated _for the generic_, not for the program. Lowering now stops on errors like everything else. The local GnuCOBOL validation harness had the same guard and would refuse to compile a program carrying a warning, which meant the program most worth putting in front of a second compiler — the one with a known caveat on it — was the one it never compiled. Warnings are also no longer reported twice: lowering forwards the typechecker's list so a caller that bails on `!ir.program` has something to print, and `compile` was adding both.
- A `debit`, an `audit`, or a CICS command inside a `while` loop in a transaction threw during emission rather than generating COBOL. Every other loop and branch carried a flag saying which body emitter to use; the `while` emitter did not, so it always used the function-body one, which has no case for an effect statement.
- The generated JCL described a build that could not succeed. A program with embedded SQL got the same three-line skeleton as a plain one: no `DSNHPC` precompile, no bind, no Db2 load library, and a CICS program got no translator step. A batch program's declared files had no DD statements, so the job could not have run even after compiling. The job now carries the steps the program actually needs — translate, precompile, compile, link-edit, bind — in the order z/OS needs them, with a DD for each declared file named after the DD the generated `SELECT` assigns to, and the load module named consistently across the link-edit, the bind, and the run step. A CICS program gets no run step and says why: it is started by a transaction identifier in a region, not by `EXEC PGM`.
- The playground highlighter and the VS Code grammar had both fallen behind the lexer: `cursor` and `sensitive` were accepted by the compiler while both editors rendered them as ordinary identifiers, and the grammar had never learned `currency` or `nullable`. The parser now exports its keyword list and `tests/editor-surfaces.test.ts` compares all three, in both directions — a word the lexer does not reserve must not be highlighted as though it were.
- Six of the ten examples had no title or description in the playground picker, so they showed a directory name and an empty blurb, sorted last. The ones that needed explaining most — cursors, failures, CICS — were among them. Every example is now described, and a test fails if a new one is added without a description.
- The banking checks never looked inside a loop. `flattenStatements` descended only into `if`, so a transaction whose only posting was inside a `while`, a `for each`, or a `switch` branch had, as far as the double-entry check could see, no postings at all — and balanced trivially. Money moving inside a loop is money moving, so every nested block is now flattened.
- Passing a record to a function generated a `MOVE` into a `-Pn` field that was never declared, so the program did not compile. Record parameters are now `LINKAGE` cells the caller points at the argument, so no move is needed; an argument with no address the caller can take is `BANK-TYPE-021` rather than silently reading a different group.
- Every non-failing function paragraph ended with `GOBACK.`, so performing one ended the whole program at the first function call. It compiled perfectly and exited 0, having posted nothing — which is why it survived until a generated program was actually executed. A function paragraph now ends with `CONTINUE.`, because `PERFORM` returns at the end of a paragraph on its own.
- Two routines that each declared a local with the same name emitted two `01` items with that name, and different `PICTURE`s when the two locals had different types, so every reference to it was ambiguous. A local only one routine declares keeps its name; one that more than one routine declares is qualified with its owner, the way parameters and results already are. Qualifying only on collision keeps names inside the 30-character limit that a transaction name plus a local name can exceed.
- A `let` declared inside a `while`, a `for each`, or a `switch` branch was given no storage at all, so the generated program referenced a name it never declared. Locals are now collected from every nested block, since COBOL has no block scope and all of them need an `01` item.
- The reserved-word list covered 221 words and missed `PRESENT`, `VALUE`, `DOUBLE`, and 300 others, so a field or function with one of those names emitted COBOL the compiler rejected. It is now the union of the IBM Enterprise COBOL reserved words and every word GnuCOBOL reserves unconditionally.
- An out-of-range computed subscript was clamped to the array bound, which ran the statement against a substituted element — the exact defect the check exists to prevent. It now raises `BANK-BOUNDS-VIOLATION` where a handler can see it. `BANK-BOUNDS-STATUS` still records `"23"` for an operator reading a dump.
- A ledger amount wider than `PIC S9(16)V99` was truncated silently by the generated `MOVE`. It is now `BANK-LED-004`, closing a gap ADR-0003 had recorded but not enforced.

- Added the comparison operators `<`, `<=`, `>=`, `==`, and `!=`. Previously `>` was the only one, which made most banking conditions impossible to express. Ordering stays decimal-only; equality also works on strings and bools.
- Added the logical operators `&&`, `||`, and `!`, with a full precedence chain: `||`, `&&`, comparison, additive, multiplicative, unary.
- Added multiplication, which adds the operand scales, and `BANK-DEC-004` when the result needs more digits than the declared precision allows.
- Added `round(expr, "MODE")` and `divide(a, b, "MODE")` covering seven COBOL rounding modes. A bare `/` is rejected as `BANK-DEC-003`, and a narrowing assignment without rounding is `BANK-DEC-002`. Rounding lowers to `COMPUTE ... ROUNDED MODE IS`, taking the scale of the assignment target exactly as COBOL does.

### Fixed

- Fixed CICS response variables being referenced but never declared in working storage, so a generated CICS program named data items that did not exist. Found by compiling the translated output for the first time.
- Fixed COBOL reserved words being emitted as record and paragraph names; the mangling previously applied only to field names.
- Fixed paragraph names colliding with data names, which COBOL treats as one namespace. A transaction named `total` alongside a field named `total` now emits `TOTAL-PARA`, and only when it would actually collide.
- Fixed COBOL file names colliding with record type names, which happens whenever a file and its record share a name. File names are now suffixed `-FILE`.
- Fixed decimal literal precision being computed below its own scale, so `0.00` was typed `decimal<1, 2>` and rejected everywhere.
- Fixed string literals being compared by exact length rather than fitting any field long enough to hold them.
- Fixed currency rejecting multiplication by a plain decimal. Scaling money by a dimensionless rate is a normal banking operation and keeps the currency; adding across types is still `BANK-DEC-005`.
- Fixed `round()` rejecting currency operands.
- Fixed nested group items reusing COBOL level 05 instead of stepping to 10, which `OCCURS` made fatal.
- Fixed source map field attribution, which assumed one emitted line per record field. Enums, nullables, and arrays emit several, and `BANK-GEN-006` caught the drift. Field start lines are now recorded as they are emitted, closing the gap noted when that check was added.
- Fixed FD records being emitted as opaque buffers. They now carry the real field structure with qualified references, so per-field mapping works.
- Fixed string literals being typed by their exact written length, so a literal now fits any string field long enough to hold it. COBOL `MOVE` pads with spaces, so this is not a silent truncation.
- Fixed function parameters never being declared in working storage. A parameter reference only resolved when it happened to share a name with a record field, so `validateAmount(amount)` read the record's `AMOUNT` rather than its argument, and calling a function was impossible. Parameters now get their own storage; record parameters resolve to the record group item.
- Fixed decimal literals being typed by their written width, which forced `0000000000000025.00` to assign to a `decimal<18, 2>`. A literal now widens to any decimal with the same scale and enough precision. The scale must still match exactly, because changing scale is a rounding decision.
- Fixed generated COBOL for functions whose body is an `if` / `else`. A `GOBACK.` was emitted inside each branch, and the period terminated the COBOL sentence, leaving the following `ELSE` and `END-IF` dangling. GnuCOBOL rejected the batch-interest-accrual output with `syntax error, unexpected ELSE`. Return statements now assign only the result field and each paragraph ends with a single `GOBACK.`. The batch-interest-accrual golden fixture is updated to match; the account-transfer fixture is unchanged.
- Fixed `bankc layout <project>` so it writes the JSON layout report as well as the markdown report.
- Fixed the command help text and CLI routing so the new commands are discoverable and executable.
- Fixed GitHub Actions CI so pnpm is installed before `actions/setup-node` tries to resolve `cache: "pnpm"`.
