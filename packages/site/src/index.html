Write your banking logic. Get COBOL the mainframe team can read.

BankLang is a compiler. You write the program in BankTS, a small language that borrows TypeScript's syntax, and it emits IBM Enterprise COBOL, a copybook for every record, and the job that builds and runs it. No model is involved anywhere in that: the same input produces byte-identical output every time.

COBOL handles money itself well: amounts are packed decimal, exact to the penny. What it has no concept of is bookkeeping. A transfer that debits one account and credits another a different amount is, to a COBOL compiler, two perfectly correct statements. BankLang knows they are the two halves of one posting, and refuses to build the program.

Why generate COBOL instead of replacing it

Banks keep balances, interest and settlement in COBOL programs that have been running for decades. The hard part of replacing them is exactness: thirty years of small, specific rules live in that code and in no other document, so a rewrite has to rediscover all of them before it can switch over. That is where the big programmes usually stall.

Between keeping the COBOL forever and replacing it there is a duller third option: keep producing COBOL, and change what produces it. The mainframe goes on running COBOL. The people who sign the code off go on reading COBOL. What changes is the language a developer writes in, and whether the expensive mistakes are still possible in it.

The COBOL it produces

Interest is a balance times a rate, rounded. Which way you round decides who ends up a penny short, so the compiler makes you say which rule to apply and then writes the arithmetic out.

Enterprise COBOL offers one rounding phrase, ROUNDED, which rounds a half away from zero. Banker's rounding, where a half goes to the even digit, has to be written out as arithmetic. Those lines are executed and compared against exact arithmetic at every boundary case, for a product and for a quotient, in all seven rounding modes.

Scale is part of the type here, so the rounding is required rather than available. A balance times a rate has six decimal places and money holds two, which makes the product a different type from the field it is going into. round is what converts it, and naming the mode is how the program says what becomes of the other four digits.

The ON SIZE ERROR branch answers a different question: a result too large for the field at all. COBOL discards the high-order digits in that case, so an overflow arrives as a plausible small number rather than an obviously wrong one. The generated branch ends the step instead.

What happens to the COBOL you already have

Nobody starts from nothing. This is the classic sequential master update: read last night's transactions, apply each one, write out the new balances and a file of the ones that failed.

The original opens four files in one statement and never learns whether any of them opened. Not one of the four SELECT statements declares a FILE STATUS field, so there is nowhere for a failure to be reported. A missing input gives file status 35, the first read hits AT END, and the step closes its files and ends with return code zero. A night that applied nothing looks exactly like a night that had nothing to apply.

The BankTS declares the same four files and gives each one a status the program has to handle. Record layouts are untouched, field for field, so the same datasets are read under the same DD names, and nothing about the data changes. What changes is that the step now ends with 12 when a file failed and 4 when it applied nothing, so the next step's COND= can tell those apart from a good night.

What it is not

  • It has never run on a mainframe. Every example compiles with GnuCOBOL, under a dialect configured to Enterprise COBOL 6.4 and under GnuCOBOL's own default. GnuCOBOL is a good open-source compiler, and the places where it and IBM's disagree are written down.
  • No money has moved through it. No bank has used it. There is no production deployment and no pilot.
  • It covers a narrow subset. Batch and CICS programs reading QSAM, VSAM and Db2, with a ledger and audit interface it defines itself. It does not replace a core banking package.
  • {{EXECUTED_COUNT}} of {{EXAMPLE_COUNT}} examples are actually run, against a reference runtime kept in the repository. {{ASSERTED_COUNT}} of those are checked against balances somebody worked out by hand. The rest are run twice, by two independent implementations, and compared: that catches a program that is wrong and would not catch one that is wrong the same way twice.
